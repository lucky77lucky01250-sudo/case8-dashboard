## D-1. リピート率の期間軸（2026-08-19 確定）

**決定: 月次と期間累計の両方を画面に出す。**

| 表示場所 | 指標 | 定義 | サンプルCSVでの値 |
|---|---|---|---|
| KPIカード・月次推移グラフ | 月次リピート率 | その月に購入した顧客のうち、それ以前の月にも購入がある顧客の割合 | 9月 0.0% / 10月 38.5% / 11月 46.7% |
| 期間サマリー（別枠） | 期間累計リピート率 | 期間内で2ヶ月以上購入した顧客の割合 | 28.6%（28人中8人） |

**理由**: 提案書42〜43行が「3大KPIを前月比つきカード＋月次推移グラフ」と約束している一方、
リピート率の定義（提案書第7項「複数月にわたって購入されたお客様の割合」）は複数月をまたいで
初めて判定できる指標で、月ごとの点を作れない。READMEの正解値28.6%も3ヶ月まとめて1個だけ出る数字。
月次に落とすには定義の読み替えが必要になるが、読み替えた数字は28.6%とは別物になるため、
検収（提案書第9項(1)「Excelと数値が一致すること」）の照合先として28.6%を画面に残す。

**実装上の注意**: 2つの数字が同じ「リピート率」の名前で並ぶため、画面には必ず定義文を添える。
9月は比較対象の過去月がないため 0.0%（前月比は「—」）。

## D-2. SKUランキングの基準（2026-08-19 確定）

**決定: 売上ベース（`ORDER BY SUM(revenue) DESC`）。講義SQLの数量ベースは採用しない。**

**理由**: 数量ベースだと単価3,800円のTシャツが1位、ウールコートが7位まで沈み、
READMEが「読みどころ」とする「11月に冬物アウターが牽引」がランキング上で見えなくなる。
AI分析の題材として機能させるため売上ベースを採る。

| 順位 | 数量ベース（講義） | 売上ベース（採用） |
|---|---|---|
| 1 | オーガニックコットンTシャツ 14点 | ウールコート ¥148,800 |
| 2 | リネンブラウス 9点 | ダウンジャケット ¥138,600 |
| 3 | レザーベルト 8点 | リネンブラウス ¥61,200 |

なおサンプルCSVのSKUは8種のみ。「トップ10」は8件表示になる。

## D-3. 講義サンプルコードから意図的に変えた点

講義コードをそのまま採用しない箇所。理由なしに講義版へ戻さないこと。

| # | 講義 | 本実装 | 理由 |
|---|---|---|---|
| 1 | `order_date: z.string().transform(s => new Date(s))` | 文字列のまま検証し、月次集計は `YYYY-MM` の文字列スライス | `new Date("あいうえお")` は Invalid Date という有効なDateを返すため日付不正を検出できない。また `"2025-09-03"` はUTC解釈・`"2025/09/03"` はローカル解釈で基準がズレ、月境界がタイムゾーン依存になる |
| 2 | `revenue/cost: z.coerce.number().nonnegative()` | 空文字・空白を無効行として明示的に弾く | `Number("") === 0` のため空欄が「売上0円の有効行」として集計に混入し、無効行にも計上されない |
| 3 | `.nonnegative()` | マイナス値を許容（返品・キャンセル行） | ECの実データには返品行が含まれる。弾くとExcelと合わない。※クライアント確認事項 |
| 4 | `invalid.push({ row: i + 2 })` | パース前の実CSV行番号を保持 | `skipEmptyLines: true` で空行が飛ぶとインデックスと実行番号がズレ、スキップ行CSVが実際と食い違う |
| 5 | `Papa.parse` の `errors` 未使用 | `errors` も無効行として集約 | 列数不一致などパーサレベルの異常が握りつぶされる |
| 6 | `category: z.string().optional()` | 必須。欠損は「未分類」にフォールバック | 任意のままだとカテゴリ別合計と売上合計が一致せず検収基準(1)に抵触 |
| 7 | カテゴリ別 `LIMIT 5` | 全カテゴリを集計 | 5種を超えると合計が合わなくなる |
| 8 | `response.content[0].text` | 型ガードを噛ませる | `ContentBlock` のユニオン型のため `pnpm type-check` が落ちる |
| 9 | `JSON.parse(extractJson(text))` | Tool use による構造化出力 | 正規表現での後追い抽出では提案書の「JSON構造化で型を固定」を満たさない |
| 10 | AI応答をSnapshot | 集計結果とプロンプト入力JSONをSnapshot | AI応答は非決定的でCIが不安定になる。出力品質は提案書どおり人手判定（5本中4本） |
| 11 | 納期10営業日 | 14営業日 | CLAUDE.md 記載の確定仕様 |
| 12 | 折れ線は売上1本 | 3大KPIを3本 | 提案書43行の約束 |

## D-5. AI分析の実装（2026-08-19 確定）

**モデルは `claude-opus-5`。** 講義記載の `claude-sonnet-4-6` は使わない。
月1回・入力2千トークン程度の呼び出しなので、提案書の月500円に十分収まる。

**JSON構造化は Tool use ではなく構造化出力（`output_config.format`）で行う。**
zod スキーマを正本にして `z.toJSONSchema()` で JSON Schema を生成するため、
スキーマの二重管理が起きない。講義の `JSON.parse(extractJson(text))` は採用しない。

**外部送信するデータは集計後の数値のみ。** 提案書 第8項の
「個々のお客様のIDや氏名は送信いたしません」を満たすため、`buildAnalysisInput()` を
必ず経由する。顧客IDと注文日が payload に含まれないことを tests/ai.test.ts で検証している。

**Snapshotテストの対象は AI の出力ではなく入力。** AI応答は非決定的でCIが不安定になるため、
固定するのは集計結果とプロンプト入力JSON。出力品質は提案書どおり人手判定（5本中4本）。

**APIキー未設定時はモックを返す。** キー到着前でも画面と検収の流れを確認できるようにするため。
モックは集計値から機械的に組み立てるので実データと矛盾しない。画面に仮である旨を明示する。

## D-7. AI分析の実測（2026-08-21）

APIキー接続後、サンプルCSV（40件）で実際に `claude-opus-5` を呼び、
検収基準の予行演習を行った結果。

### コスト実測

1回の呼び出しで `input=1,074 / output=1,414 / cacheRead=978` トークン。
**$0.0412（約6.4円）**。呼び出しごとに `lib/ai/cost.ts` がサーバーログへ記録する。

| | 1回あたり | 月1回運用 |
|---|---|---|
| 実測 | 約6.4円（キャッシュ命中時） / 約7.3円（キャッシュ無効時） | **約7円** |
| 提案書の計上 | — | 500円 |
| 講義版の想定 | — | 1,000〜2,000円 |

**提案書の月500円はそのまま据え置く。** 実測の70倍の余裕があるが、
クライアントが月に複数回アップロードしたり再生成したりする可能性、
および将来の価格改定を吸収する上限値として妥当なため。
検収で費用を問われたら「実測は月7円程度、500円は余裕を見た数字」と答えられる。

コストの86%は出力トークンが占める。入力側のプロンプトキャッシュ（`cache_control`）は
TTLが5分なので月1回運用では命中せず、逆にキャッシュ書き込み分だけ約0.2円高くなる。
それでも残している理由は、**検収基準(2)(3)が要求する「コメント5本の連続生成」で命中するから**。
月次運用での0.2円の損より、検収時の節約と応答速度のほうが効く。

### 検収基準の予行演習（5本生成）

同じデータで5本生成し、述べられた**金額168件・比率150件**を正解値と機械的に突き合わせた。

| 検収基準 | 合格ライン | 結果 |
|---|---|---|
| (2) AIコメントが事実と矛盾しない | 5本中4本 | **5本中5本**（事実誤認ゼロ） |
| (3) アクション提案が検討に値する具体性 | 5本中3本 | **5本中5本**（全25件がSKU名・数量・期限・確認指標つき、一般論ゼロ） |

5本すべてが「11月にアウターが牽引」を正しく読んでおり、READMEが読みどころとした点を拾えている。
1本は9〜11月で粗利率が62.9%→62.8%→61.6%と低下していることを指摘した。
アウター2品（粗利率60.5%・61.6%）が他より低いため、売上が伸びても粗利率が下がるという
こちらが用意していなかった観点で、内容も正しい。

**注意: これは同一データでの予行演習。** 提案書 第9項の(2)(3)は
「納品時に実際のデータでコメントを5本生成し、担当者様と一緒に1本ずつ確認」する人手判定であり、
この結果がそれを代替するものではない。

## D-8. ヘルスチェックで `head: true` を使ってはいけない（2026-08-21）

Supabase 接続直後、テーブル未作成の状態で `/api/health` を叩いたところ
**HTTP 200「正常」が返った**。実際には Supabase 側が 404 を返している。

### 再現

| 実装 | Supabase の応答 | supabase-js が返す値 |
|---|---|---|
| `select("id", { count: "exact", head: true })` | HTTP 404 `PGRST205` | `error: null` / `status: 204` |
| `select("id").limit(1)` | HTTP 404 `PGRST205` | `error: PGRST205` / `status: 404` |

`head: true` は本文を返さない HEAD リクエストを発行するため、supabase-js が
エラー本文を読めず「成功」として返す。`{ count: "exact", head: true }` は
行数だけ知りたいときの定番の書き方だが、**死活監視の宛先に使うと監視が嘘をつく**。

### 対処

1. `head: true` をやめ、`select("id").limit(1)` にする
2. `error` だけでなく **HTTPステータスも確認する**（`error || status >= 400`）
3. `error: null` かつ `status: 404` のケースを回帰テストに追加（tests/health.test.ts）

これを見逃していた場合、UptimeRobot は Supabase が落ちても「正常」と報告し続け、
提案書 第9項(4)「失敗に気づけること」を満たさない状態のまま納品していた。

## D-9. Supabase の公開サインアップは必ず無効にする（2026-08-21）

Supabase プロジェクト作成直後の初期状態は**公開サインアップが有効**だった。

RLSポリシーは `for select to authenticated using (true)`、つまり
「ログイン済みなら全データを読める」設計になっている。読み手が7名に固定されており、
アカウントは管理者が作成する運用を前提にしているため。
この前提が崩れる（＝サインアップが有効）と、**第三者が自分でアカウントを作って
ログインし、クライアントの売上データを全て閲覧できる。**

対処として Authentication → Sign In / Providers の
「Allow new users to sign up」を OFF にした（同じ画面の「Allow anonymous sign-ins」も
OFF であることを確認。有効だと誰でも authenticated になれる）。

**設定は画面上の表示を信じず、実際に試行して確認する。**
`pnpm verify:supabase` が以下を毎回実行する。

- 未ログインで各テーブルを読めないこと
- 未ログインで書き込めないこと（42501 で拒否）
- `/auth/v1/signup` が 422 `Signups not allowed` を返すこと
- 公開サインアップ・匿名サインイン・メール確認の各設定値

パスワードの最低文字数は初期値6文字だったため引き上げた。

### 残課題

パスワード再設定の導線が無い。管理者がアカウントを作り直すしかない状態。
読み手7名（うち営業5名）で必ず発生するため、納品前に方針を決める。
選択肢はパスワード再設定画面の実装か、マジックリンクへの切り替え。
どちらも本番用SMTPの設定が必要。

## D-10. DBからの読み出しは必ずページングする（2026-08-21）

PostgREST（Supabase の REST API）は**1回のクエリで最大1,000行しか返さない**。
上限を超えた分はエラーも警告もなく切り捨てられる。

サンプルCSVは40件なので開発中は気づかない。本番の売上明細が1,000行を超えた瞬間に
**合計金額が実際より小さい値で表示される**。しかも画面上は何事もなく成功して見える。
提案書 第9項(1)「画面の数字が既存Excelの数値と一致すること」を静かに壊す経路。

### 対処

`lib/supabase/paginate.ts` の `fetchAllPages` を必ず経由する。
`.range(from, to)` を返却件数がページサイズ未満になるまで繰り返す。

この関数は `server-only` を import していない。テストから直接呼べるようにするため。

### 検証

- 単体テスト6件（tests/paginate.test.ts）— 2,500行・ちょうど2,000行・0件などを固定
- 結合テスト（tests/integration/persistence.test.ts）— 実Supabaseに2,500行を保存し、
  読み出した行から計算した集計が保存前と完全一致すること、金額合計が1円も変わらないことを確認

結合テストは `pnpm test:integration` で個別に実行する。CIにはシークレットを置かないため
既定の `pnpm test` からは除外している。

## D-11. 保存の目的は「アップロードした人以外も見られること」（2026-08-21）

読み手は7名だが、CSVをアップロードするのは担当者1名だけ。
保存していないと、残り6名は数字を見るためにCSVを受け取って自分でアップロードする必要がある。
それでは「月次レポート作成の手間をなくす」という提案の前提が崩れる。

保存後は画面を開くだけで最新の数字が出る。

**保存に失敗したときに「保存済み」に見せない。** 画面には
「保存中／保存済み／未保存（この画面を閉じると失われます）」を表示する。
数字自体は正しいので画面から消しはしないが、状態は正直に伝える。

明細の保存が途中で失敗した場合は `uploads` のレコードも削除する。
「40行成功」と表示しながら実際には30行しか入っていない状態を残さないため。
