## 概要

売上CSVをアップロードすると、KPI・グラフ・AI分析コメントを表示するダッシュボードを作りました。本番公開まで行い、ローカルでは再現しない不具合を3つ修正しています。

## A. 課題概要

**課題名**

案件8「AI搭載 売上分析ダッシュボード」のStep 3（実装）です。Step 1のヒアリングとStep 2の提案書は提出済みで、今回はその提案書に書いた約束を実際に満たす工程にあたります。

**課題要件**

架空のアパレルEC「株式会社LUMINA」向けに、月次の売上分析ダッシュボードを作ります。先方の課題は、月次レポートの作成に毎回3時間かかっていることです。CSVの整形、グラフ作成、コメント執筆を毎月手作業で繰り返しています。これを約30分に短縮するのが目標です。

作る機能は次の7つです。

- CSVアップロード（ドラッグ&ドロップ、列の並びが違っても自動判定）
- 売上・粗利・リピート率の3大KPIを前月比つきで表示
- 月次推移グラフ
- カテゴリ別売上の内訳
- SKU売上トップ10ランキング（SKUは商品の管理単位）
- AI分析コメント（現状サマリーと翌月のアクション提案）
- ログイン機能

**実装条件**

納期は14営業日、初期費用は44万円（税込）、月額は約3,900円です。レポートの読み手は社長、マーケティング部長、営業担当5名の計7名で、データ分析の専門家ではありません。期間軸は月次のみとし、日次表示はPhase 2に回しました。ブランドカラーは白とネイビーです。

提案書には検収基準を4つ書きました。この4つを満たすことが実装のゴールになります。

- 画面の数値が、同じ定義で計算した既存Excelの数値と一致すること
- AIコメントが事実と矛盾しないこと（5本中4本以上で合格）
- アクション提案が社内で検討できる具体性を持つこと（5本中3本以上で合格）
- 失敗に気づけること（最終更新日時の表示と、外部監視からの通知）

4つ目が今回の肝でした。動くものを作るだけでなく、壊れたときに人が気づける状態まで作るのが条件です。

## B. 実装内容

**使用技術**

- Next.js 16（App Router）、React 19、TypeScript
- Tailwind CSS v4
- Recharts（グラフ描画）
- Supabase（データベースとログイン）
- Claude API（claude-opus-5）
- Vercel（公開先）
- GitHub Actions（テストと自動デプロイ）
- Vitest（テスト）

**実装した機能**

提案書に書いた次の7つを実装しました。

- CSVアップロード
- 3大KPIカード
- 月次推移グラフ
- カテゴリ別売上
- SKU売上トップ10ランキング
- AI分析コメント
- ログイン機能

これに加えて4つ足しました。提案書の検収基準にある「失敗に気づけること」を満たすためです。

- ヘルスチェックAPI（Supabaseへ実際にクエリを投げ、成功なら200、失敗なら500を返す）
- 外部監視（UptimeRobotが5分間隔で確認し、異常時にメールを送る）
- Supabase停止対策（Vercel Cronが毎日1回アクセスする）
- 独自SMTP（Resendから独自ドメインでメールを送る）

Supabaseの無料プランは1週間アクセスがないと自動停止します。これを放置すると、保守契約が切れたあとに誰も気づかないまま止まります。

**工夫したポイント1: リピート率を2種類出した**

リピート率は定義が1つに決まりません。そこで2種類を並べて表示しました。

月次リピート率は「その月に購入した顧客のうち、それ以前の月にも購入がある顧客の割合」です。期間累計リピート率は「期間内で2ヶ月以上購入した顧客の割合」になります。同じ11月のデータで前者は46.7%、後者は28.6%と18ポイント以上ずれました。

どちらが正しいかを決めるより、読み手7名が同じ数字を見て同じ解釈をすることが重要だと考えました。画面のカードの下に定義文を常時表示しています。

**工夫したポイント2: AIに顧客情報を渡さない**

AIに送るのは集計後の数値だけにしました。提案書で「個々のお客様のIDや氏名は送信しない」と約束したためです。売上データをそのまま渡さず、月別の合計値やカテゴリ別の内訳に変換してから送っています。

この約束が守られているかは、テストで自動検証しています。「顧客IDが1件も含まれない」「注文日が含まれない」という2つのテストを書きました。約束を文章で書くだけでは、後の改修で崩れたときに誰も気づけません。

**工夫したポイント3: 取り込めなかった行を持ち帰れるようにした**

スキップした行は、件数だけでなく内容も返します。「40行成功 / 0行スキップ」の表示に加えて、スキップした行と理由を一覧で出し、CSVとして保存できるようにしました。

件数だけを出すと、利用者は「なぜ合計が想定と違うのか」を自分で調べられません。結果として問い合わせが発生します。原因の行と理由が手元にあれば、その場で修正して再アップロードできます。

## C. 実装過程

**開発の流れ**

最初にやったのは実装ではなく、サンプルデータの検証です。

講義のサンプルCSVには、正解値としてREADMEに月次売上・粗利・カテゴリ別・リピート率が用意されていました。この数字をそのまま信じず、CSVから自分で再計算して突き合わせています。前の案件で講師から「正解値そのものを原文と突き合わせて疑う」というフィードバックを受けていたためです。

売上・粗利・カテゴリ別は一致しました。一方でリピート率は定義が書かれておらず、計算方法によって値が変わることが分かりました。作ってから定義のずれに気づくと、集計もグラフも作り直しになります。

そのあと Supabase、Next.js、Vercel の順に構築しました。ローカルで一通り動くことを確認してから本番に公開しています。

公開後、画面の数値をCSVから独立に再計算して突き合わせました。KPIカードの6項目、SKUランキング8件の売上と数量、カテゴリ別売上の並び順がすべて一致しています。AI分析コメントに含まれる数値も検証しました。2回の生成で16項目と18項目を確認し、いずれも不一致はありません。

**AIへの質問内容**

実装はClaude Codeに任せ、判断が必要な場面だけ説明を受けて自分で決める進め方にしました。

決めたのは主に2つです。1つはリピート率の定義で、月次と期間累計の両方を出す方針を選びました。もう1つはSKUランキングの基準で、数量ベースではなく売上ベースにしています。

AIに出させたのは選択肢と、それぞれを選んだ場合に何が起きるかです。「どちらがいいですか」と聞くより「それぞれ選んだ場合どうなりますか」と聞くほうが、自分で判断する材料が集まりました。

**エラー1: 本番だけ全ページが500になった**

デプロイは成功したのに、本番のすべてのページが500エラーを返しました。ビルドエラーもテスト失敗もありません。

原因は、Vercelに登録した環境変数5つをすべて「Sensitive」属性にしていたことでした。Sensitiveな変数は、あとから値を読み出せません。ビルド手順はVercelから環境変数を取得してからビルドする流れです。そのため取得できたのは11文字のプレースホルダで、本来の値ではありませんでした。

`NEXT_PUBLIC_` で始まる変数は、ビルド時にソースコードへ文字列として埋め込まれます。プレースホルダのまま埋め込まれた結果、実行時にデータベースへ接続できず、全リクエストが例外になりました。

厄介なのはビルドが成功することです。プレースホルダも文字列としては正当なので、型チェックもテストも通ります。壊れていると分かるのは本番にアクセスした瞬間だけでした。しかもエラーは「データベースに繋がらない」としか見えず、Supabase側を疑って時間を使いました。

解決は、`NEXT_PUBLIC_` の2つを非Sensitiveで登録し直すことです。この2つはもともとブラウザに配信される前提の値で、隠す意味がありません。公開してよい値だけが `NEXT_PUBLIC_` を名乗れます。そして `NEXT_PUBLIC_` を名乗る値は隠せません。

**エラー2: 最終更新日時が9時間ずれた**

CSVをアップロードした直後は「22:59」と表示され、ページを再読み込みすると「13:59」に変わりました。同じ1件のデータが9時間前の時刻として表示されます。

原因は `toLocaleString("ja-JP")` の使い方でした。`"ja-JP"` は書式の指定であって、タイムゾーンの指定ではありません。省略すると実行環境のタイムゾーンが使われます。

アップロード直後の表示はブラウザ側で作られるため日本時間になります。再読み込み後の表示はVercelのサーバー側で作られるため、UTCになりました。

この不具合はローカルでは絶対に再現しません。開発サーバーはサーバーもブラウザも同じマシンで動くので、どちらも日本時間だからです。

解決はタイムゾーンを `Asia/Tokyo` に固定することでした。あわせて回帰テスト（同じ不具合が再発したら失敗するテスト）を書いています。GitHub Actions のテスト環境は世界標準時で動くため、タイムゾーンの指定を外すとテストが落ちます。実際に修正を戻して2件落ちることまで確認しました。

**エラー3: データベースが壊れてもヘルスチェックが200を返した**

外部監視の宛先として、Supabaseへクエリを投げるヘルスチェックAPIを作りました。ところがテーブルが存在しない状態でも、正常を示す200を返し続けます。

原因は、件数だけを取得する `head: true` というオプションでした。この指定はHTTPのHEADリクエストになり、応答に本文が含まれません。Supabaseは「テーブルが存在しない」というエラーを本文で返します。その本文が届かないため、ライブラリはエラーなしとして扱っていました。

監視の宛先がこの挙動だと、データベースが壊れていても永久に気づけません。監視を入れているという安心感だけが残ります。これは監視がない状態より危険です。

解決は本文を返す通常のクエリに変え、エラーの有無とHTTPステータスの両方を見るようにすることです。ステータスが400以上なら失敗と判定します。「エラーが返ってこないこと」と「成功したこと」は別だという前提でコードを書き直しました。

**AI出力の表記が揺れた**

本番で生成したAIコメントの中で、同じ287,400円が「51.3%」と「51.2%」の2通りで書かれていました。正しくは51.2665%で、四捨五入なら51.3%、切り捨てなら51.2%です。どちらも誤りではありません。

ただ、社長がサマリーと提案文を並べて読んだとき「同じ金額なのに数字が違う」と受け取ります。数字を信頼してもらうことがこのダッシュボードの価値なので、一度疑われると正しい部分まで疑われます。

解決はプロンプトに1行足すことでした。丸め方の指定だけでなく「同じ値は同じ表記にする」という一貫性の要求も書いています。実際に起きたのは丸め方の誤りではなく、1つの出力の中での不一致だったためです。

## D. 学習の振り返り

**今回学んだこと**

一番の収穫は「ローカルで動く」と「本番で動く」が別だと体感できたことです。今回見つけた不具合のうち3つは、ローカルでは再現しませんでした。

環境変数の渡され方とタイムゾーンは、実行環境によって変わります。ヘルスチェックの誤判定は、テーブルが壊れた状態を作らないと表面化しません。いずれも正常なローカル環境で動かしているだけでは出てこない種類でした。

本番に出して実際に触るまで、存在に気づけません。だからこそ、早く本番に出して自分で通しで確認することに価値があると分かりました。

2つ目は「エラーが返ってこないこと」と「成功したこと」は違うという点です。ヘルスチェックはエラーがないことを成功とみなしていました。実際にはエラーを読めていなかっただけです。この区別を意識せずに書いたコードは、失敗を見逃す方向に倒れます。

3つ目は、正しい数字でも表記が揺れると信頼を失うという点です。51.3%と51.2%はどちらも誤りではありません。それでも同じ金額に違う数字が付いていれば、読み手は数字全体を疑います。技術的な正しさと、読み手が受け取る信頼は別物でした。

**参考にした資料**

Next.js、Vercel、Supabase、Anthropic の公式ドキュメントを中心に参照しました。特に Next.js はバージョンによる差が大きい点に注意が要ります。インストールしたパッケージに同梱されているドキュメントを読みました。ウェブ検索で出てくる情報は古いバージョン向けのことがあり、そのまま使うと動きませんでした。

**作った機能と発展アイデア**

実装した機能は次のとおりです。

- CSVアップロード（ドラッグ&ドロップ、スキップ行の一覧とCSV出力つき）
- 3大KPIカード（売上・粗利・リピート率、前月比つき）

発展アイデアは2つ考えています。

異常検知アラート → マーケティング部長が、前月比±20%の変化を翌朝に知れます。月次レポートを待つ場合と比べて、打ち手が最大1ヶ月早くなります。

Shopify API直接連携 → 担当者がCSVを扱う工程ごとなくなります。アップロードのし忘れによる「先月の数字のまま報告する」事故を、構造的に防げます。

**次の課題に向けて**

次は Step 4 の納品と、講座最終課題であるROI分析レポートです。「動くものを作った」ではなく「月何時間削減し、投資が何ヶ月で回収できるか」を数字で示す文書になります。

今回の案件で、作る力については一区切りつきました。ここからは、作ったものの価値を非エンジニアに伝える力が課題になります。ダッシュボードの数字が正しくても、その価値が経営層に伝わらなければ次の発注にはつながりません。
